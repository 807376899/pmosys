# PMO 项目生命周期需求基线

## 1. 文档规则

- 本文是 PMO 项目生命周期的当前有效需求来源；实现、测试和后续需求变更均以本文为准。
- 有效需求变更必须同时更新本文、`decision-log.md` 与 `acceptance-checklist.md`。
- 本文不把系统外的线下会议、采购或发文流程误写为系统内审批功能；系统负责登记、校验、留痕与统筹可见性。

## 2. 首期目标与边界

首期建立 PMO 主视角的项目状态流转、动态评审批次、可配置细进度、角色门禁与可追溯历史。

首期不实现供应商、合同、验收材料和报销材料的实体关联；但数据模型和需求设计必须为后续多对多关系预留扩展位置。

## 3. 项目基础信息

项目包含至少：项目名称、所属学院（部门）、所属专业、项目负责人、预算、地点、类型、状态。

测试阶段中，学院（部门）、专业、地点和类型均允许自由填写；后续将提供可配置目录和统一选项，且不得破坏既有项目的历史值。

## 4. PMO 四大统筹视图

四大类由当前项目状态自动归属，用于工作台筛选与统计，不是用户可手动编辑的分类字段。

| 统筹视图 | 自动归属规则 |
| --- | --- |
| 未立项 | 申报、PMO 审核、待评审、评审、评审退回待修改、待立项发文等状态 |
| 项目库 | 已登记立项文件号且已进入项目库的未实施、计划实施、实施、验收等状态 |
| 已完成 | 已完成验收，且由 PMO 完成材料完备确认的项目 |
| 已废弃 | 已按废弃规则完成废弃流转的项目 |

除“已废弃”外，项目只能通过合法状态流转自动进入相应统筹视图，不能直接切换类别。

## 5. 主阶段与细进度

### 5.1 未立项

1. **申报中**：草稿和学院内审核属于同一主阶段。学院的审核、补正、确认等工作通过可配置细进度记录；首次提交 PMO 时学院流程视为已完成。
2. **PMO 审核与交互修改**：PMO 审核申报书和相关材料，并可与申报方进行交互修改。
3. **待评审项目池**：通过 PMO 审核但尚未被纳入某一评审批次的项目。
4. **评审中**：项目被选入已开启的评审批次后进入该状态。
5. **评审退回待修改**：评审未通过后保留为独立状态，保存评审批次、意见和退回原因；修改后须重新提交 PMO，才可再次进入待评审项目池。
6. **待立项发文**：全部配置的评审步骤通过后进入该状态。

### 5.2 项目库

PMO 录入立项文件号、登记操作人和登记时间后，项目自动进入项目库，默认状态为**未实施**。立项发文可在系统外完成；本系统不要求在线完成发文审批。

项目被明确选择进入计划实施后，才进入实施序列。实施序列至少支持：计划实施、采购文件编制、外部采购流程、供应商实施、实施验收和材料完备确认。

### 5.3 细进度

- 细进度从所属主阶段的模板生成，可按工作流版本配置新增、停用、排序和说明。
- 首期细进度仅用于跟踪，不自动阻断主阶段状态流转。
- 每项细进度至少记录状态、负责人、计划日期、完成日期、说明和更新时间。

## 6. 可配置评审与动态窗口

- 评审流程不是固定“三轮”。每个工作流版本维护一条可新增、删除、排序的评审步骤链。
- 每个评审步骤可独立开启评审批次/窗口。当前默认步骤可包括：校外专家评审、实验室建设与管理委员会评审、校长办公会及党委会审议。
- PMO 只能从待评审项目池选择部分项目纳入某个已开启批次；未选中的项目继续留在项目池。
- 项目通过当前步骤后进入下一配置步骤；所有步骤通过后进入待立项发文。
- 校内相关部门的旁听属于批次参与信息，不等同于审批结论。

## 7. 角色、审批与历史

- 首期提供预置角色并允许 PMO 新增、停用和维护：申报单位、PMO、评审秘书、评审专家/委员会、校级会议等。
- 流转规则按角色限制发起或审批，并记录操作人、审批人、时间、理由、意见和交付物/外部文件号。
- 系统暂不实现真实账号登录、待办、多人会签；但接口和历史记录须保留未来接入的扩展位。
- 所有工作流配置采用版本化：新项目使用新版本；存量项目保留原版本，PMO 可执行并留痕的单项或批量迁移。

## 8. 完成与废弃

- 项目验收完成后，PMO 可执行“材料完备确认”，登记验收与报销材料已完备的确认信息、操作人和审批人；确认后项目自动归属“已完成”。
- “已废弃”可由任一非终态阶段直接发起；必须填写废弃原因、操作人和审批人，并保留原阶段、流转时间和完整历史。

## 9. 后续实体模块

后续采购与履约模块应支持：项目与供应商多对多、项目与合同多对多、验收材料与报销材料可被多个项目关联使用。该模块接入后，材料完备确认将由共享材料关联和完备性规则辅助或替代人工确认。

## 10. 分层治理实施规则

项目治理采用固定 Stage、ProjectWorkItem、Milestone、Batch、BusinessRecord 和 AuditEvent 分层。项目库-推进中只能由 PMO 显式纳入推进，不能由预算审核等事项自动推断。事项完成和重开均保留 Completion Record 与审计；BusinessRecord 保存事实本体，附件独立关联。

## 11. Phase 1 PMO 工作台与运行中配置

- 工作台是 Work Item 批量下发、常用事项沉淀与工作包复用的主入口；项目详情允许为单项目例外新增临时事项。
- 工作台固定展示项目、Stage、当前进展、部门/负责人、预算、下一关键节点和更新时间。当前进展按逾期、等待外部、进行中、未开始排序；同级按关注节点、计划日期和优先级排序，最多显示两项。
- 阶段跟踪表是 Work Item 投影：未立项与推进中各有推荐列；推荐列来自模板且仅影响显示，不创建事项。个人可在浏览器本地调整显示列。
- 批量操作固定在右侧原地切换：纳入推进、调整 Stage、添加事项、应用工作包；批次入口在后续 Batch 模块完成前禁用。
- 添加事项支持一次下发多个事项；每项可设置办理方式、负责人、计划日期、优先级、关注节点、说明及三种预设完成后处理（只记录完成、生成里程碑、要求固定结果字段）。不实现通用规则编辑器。
- 常用事项与工作包均须 PMO 明确保存，不自动沉淀。工作包保存的是本次下发的整个事项组合。
- 切换右侧操作或目标 Stage 时，左侧项目列表不得重新请求、排序、重挂载或丢失滚动和勾选状态。

## 12. 工作台信息层级与事项过程记录（Phase 1 修正）

- Stage 是五个固定治理口径：未立项、项目库—未实施、项目库—推进中、已完成、已废弃。Stage 单元不得附带 draft、送审中、采购中等旧小状态；并行工作只由 ProjectWorkItem 投影展示。
- 右侧批量操作台保持 sticky，但最大高度应随视口剩余空间计算。页面仍有空白时不得先出现内部滚动；预检结果合并为操作台内部区域。
- 常用事项是可搜索、可加入清单的单项复用库；工作包是一组事项的独立复用库。保存常用事项后，下一次打开添加事项必须立即可搜索复用。
- 自定义事项首屏只要求事项名称、事项内容和当前状态。负责人、计划日期、优先级、办理方式与附加备注属于折叠的“更多管理信息”；办理方式默认仅跟踪。`track_as_key_node` 在界面显示为“☆ 重点关注”。
- Completion Rule 以后果组合表达。Phase 1 只在折叠的“完成设置”中提供“记入项目里程碑”和“完成时填写结果”；`require_business_record` 仅保留后端扩展位，不展示半成品选择器。
- WorkItemProgressLog 记录尚未完成事项的连续过程，保存正文、操作人、时间和 `is_timeline_highlight`。默认只在事项自身展开区显示；只有高亮记录才投影到项目管理时间线。
- 项目管理时间线只显示 Stage 迁移、纳入推进、事项创建/完成/重开、里程碑、正式依据和高亮进展。完整 AuditEvent 通过“查看完整操作记录”折叠查询，细碎字段编辑不进入管理时间线。

## 13. 主流程排序与年度推进周期

- Work Item 的长期排序仅依赖 `flow_group` 与 `sequence_rank`。插入“某事项之后”只是创建时输入，系统计算 rank；间隔耗尽时只重排当前项目或模板同组事项，不改变业务历史。
- 下一关键节点取首个未完成主流程事项；暂停默认阻塞，完成、不适用、取消和显式跳过不参与。重点关注是独立的 PMO 关注标记。
- 取消事项不是新的状态枚举，而是保存取消时间、原因与操作人的独立历史动作。
- 每次纳入推进形成一个年度推进周期，状态为 active、deferred、completed 或 cancelled。暂缓结束本周期并回到未实施；重新纳入创建新周期。未立项项目可登记提前推进准备；获 PMO 特批时可标记“特批推进中”，但 Stage 仍为未立项，不能计入项目库—推进中。
- ProjectCategory 是管理员维护的 PMO 管理分类，用于排序、筛选和统计；ProjectType 保持项目业务类型/导入属性。类别排序按 category_sort_order → department_sort_order → 项目名称/编号；未配置值使用稳定回退。
- 治理写操作以“持久化 → API 投影 → UI 回显 → 刷新后仍存在”为验收口径。前端禁止使用浏览器原生 alert、confirm、prompt；失败时不得乐观保留成功态。
# External Constraint（2026-08-21 补充基线）

- External Constraint 是项目当前适用的外部治理条件，不是 Stage，也不是 Work Item。预算审核、备案、准入等条件的具体办理仍由 ProjectWorkItem 管理。
- 模板包含名称、推荐 Stage、是否阻断、结论字段和项目字段 effects；推荐 Stage 只用于推荐和筛选，不能限制实际建立约束。
- 项目约束在 Phase 1 仅可选关联一个主 Work Item；多对多关联后续再扩展。办理状态和解除结果通过“开始办理、要求补充、登记结论、不再适用、已有结论失效”等动作驱动，不要求 PMO 同时维护两个下拉框。
- `external_constraints_cleared` 为三态：未确认范围为 `unknown`；已确认且至少一个适用阻断约束未解除为 `false`；已确认且全部适用阻断约束已解除或不适用为 `true`。非阻断约束不影响此判断。
- 若项目没有适用阻断性 External Constraint，则 `external_constraints_cleared=true`；该指标仅说明外部治理条件明确，不代表内部采购准备工作完成。
- 有效预算统一投影为 `effective_budget`，并返回 `effective_budget_source`。来源顺序为已解除的预算核定约束、历史审核预算、初始预算。
- 批量临时约束只有在 PMO 显式选择“保存为常用外部约束”时才沉淀模板。工作台“外部约束办理中”筛选只展示范围已确认且存在未解除阻断约束的项目；四项主统计与该次级提示分别呈现。
